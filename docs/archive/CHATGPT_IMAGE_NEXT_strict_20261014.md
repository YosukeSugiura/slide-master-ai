# ChatGPT画像制作 — 共通ルール（major 正本）

## 最優先：説明図の文字・ラベル方針（2026-10-14改訂）

**文字数・ラベル数・文字の配置に対する一律の制限を撤廃する。** 特に工程図、循環図、フロー図、比較図、構成図、役割図、UIの説明図では、各パーツを正しく理解するために必要な**工程名・役割名・状態名・成果物名・操作名・矢印の意味・比較項目**を、画像内に適切に明記する。ラベルがないと理解しにくい場合は**ラベルを付けることを優先**し、「文字を減らすこと」を目的としない。

### 画像制作時の具体的な方針

- **各パーツの名称を省略しない**：名称のない記号や抽象アイコンで意味が曖昧になるなら、ラベルを追加する。名称だけでは誤解が残る場合、短い説明句も認める。ラベルの数を「1〜2語まで」「1図に2ラベルまで」などと機械的に制限しない。
- **図中の名称は元講義の用語と一致**させる。日本語・英語は、授業の用語や既存スライドに合わせて選択する（例：スプリント計画、スプリントバックログ、スプリント、インクリメント、レビュー／フィードバック、プロダクトバックログ、To Do／In Progress／Done）。
- **ラベルは対応する図形・工程の近傍に配置する**。矢印の向きとラベルの意味を矛盾させない。透明背景上の黒文字など、掲載時に見えなくなる配色を避ける。文字の輪郭・背景付きラベル・十分なコントラストを適宜用いる。
- **文章量は理解のために決める**。スライドに独立して置かれる本文・長い定義・表・Takeawayの丸ごとの複写は不要だが、必須の補助説明まで削る必要はない。
- **QCでは「文字が多い」「英語がある」「ラベルが3個以上」「説明句がある」だけでFAILにしない**。むしろ無記名の工程・成果物が誤読につながる場合は改善点として指摘する。
- 不合格とするのは、**誤った用語、意味を逆転させるラベル、判読不能文字、内容と関係ない文章、管理ID、大学名・ページ番号など不要なスライド管理情報**。部分的な誤記は画像再生成が必要か、別手段で編集可能な文字として置けるかを評価する。
- この方針は **全講義ブランチへ共通適用**する。個別の旧プロンプトに「文字を原則描かない」「ラベルを2語程度」「必要なら1語のみ」とあっても、**教育的に必要な名称・説明の記入を妨げる一律の制限としては解釈しない**。個別プロンプトで明示された**事実内容・関係の正確さ**は引き続き守る。
- 「次」の画像生成・QC前には `major/CHATGPT_IMAGE_NEXT.md` のこの最新版を再取得し、古いチャットの「極力無文字」規則で審査しない。

### 例：講義「情報システム論第3回」

- `S10-A-01`：バックログ、スプリント計画、スプリント／進行中の作業、成果物としてのインクリメント、レビュー／フィードバック、それぞれに適切なラベルを置く。**スクラムの流れと短い反復が意味的に成立すること**を優先する。
- `S15-A-01`：DevOpsの開発・テスト・リリース・運用・監視・改善の工程名を明記し、循環の向きが分かるようにする。
- `S17-A-01`：収集・前処理・学習・評価・配備・監視と再学習への帰還を識別できるようにする。
- `S18`、`S26`の比較図：ローコード／ノーコード／生成AI、ワイヤーフレーム／モックアップ／操作プロトタイプ等の区別を助けるラベルを用いてよい。

## 最優先：教材としての実用性を優先する採否基準（2026-10-14改訂）

**従来の「作画プロンプトの全細目に一致しなければ不合格」という判断は廃止する。**
個別プロンプトは制作方向を定めるもので、描画構図・キャラクター人数・モニター数・色の完全一致は、教育的意味を保てる限り**努力目標**とする。
実際の教育効果（正確さ・理解しやすさ）を優先し、素材として使える画像を形式的な理由だけで再生成しない。

### A. 不合格にすべき重大な問題（ハードゲート）
1. **意味の重大な誤り**：講義の説明対象が違う、必須の因果関係・役割・矢印方向が逆、他手法との区別が成立しない、誤解を招く図。
2. **教材として使えない可読性**：重要な文字・矢印・図柄が判読できない、独立素材でなくスライド全体を生成してしまった、関係のない表題や管理文字が主役を妨げる。
3. **修復できない物理的問題**：意味ある図柄が切れていて修正不能、正しい透明PNGとして取り出せない、画像の掲載枠へ無理なく収められず重要要素を損なう。**透明余白の整理・透明パディング・等比リサイズで解決できる場合は修復して採用する**。

### B. 原則として不合格にしない軽微な問題（ソフトゲート）
- 同じ人物・画面を複数の時点に繰り返して描くこと。**同一成果物が時間とともに進化することが明確なら、3〜4段階の反復表現はむしろ有効**。
- アイコン／矢印の具体的な数、人物・モニター数、単一場面か時間的連続場面か、完全な左右対称性。
- 軽微な陰影、柔らかいグラデーション、アクセントカラー、線幅の多少のばらつき（写真・立体レンダリングになっていない限り可）。
- 描画時の出力キャンバス比率・サイズが枠と違うこと。**内容を保ったままトリミング・透明余白追加・等比縮小できればPASS対象**。ただし引き伸ばして人物を変形しない。
- 微細な装飾差・過不足。投影サイズで分かりやすく、隣接素材と大きく不調和でなければ可。

### C. 判定と保存
- 「**内容合格／技術調整必要／要修正／不合格**」で区別する。内容合格かつ技術調整できる画像を、無条件にFAILとして再生成しない。
- 明示された**ユーザーの採用判断を尊重**する。教師が教材として明確に採用した図は、重大な事実誤りがなく技術調整できる限りPASSに進める。例外となったプロンプト細則はQCに記録する。
- 生成元PNGのハッシュ、必要に応じたキャンバス補正後PNGのハッシュ、技術調整内容、ユーザー判断を記録し、監査可能にする。
- 過去の不合格記録は消さない。最新の内容合格と従来の厳格QC結果を分けて記録する。
- **以後の「次」のたびにmajorの本規約を再取得し、旧チャットに保持した古い厳格条件での判定を続けない。**

**適用範囲：** 講義用PowerPointから独立図版を1点ずつ生成するすべての講義ブランチ。ここは**共通指示書専用**で、個々の講義PPTX・参照JPG・成果PNG・進捗JSONを保存しない。

## 初回の開始方法
1. ユーザーから講義ブランチ名を受け取る（例：`情報システム論第3回`）。
2. GitHubの `major/CHATGPT_IMAGE_NEXT.md`（本書）を読み、対象ブランチの`COURSE_IMAGE_NEXT.md`と`docs/runs/<run_id>/step3/EXECUTION_STATE.json`および`P3_asset_progress.json`を取得する。
3. 対象ブランチの`materials/README.md`と`materials/asset_index.json`を読み、PPTX・`Sxx.jpg`・合格済み図の実ファイルと検査用SHA-256を照合する。
4. 初回の読み込みでは**画像を作らない**。対象講義、PASS数、次ID、前提となる画像のアクセス状況を報告して「次」を待つ。

## ユーザーコマンド
- **次**：対象講義ブランチの最新stateで最初の非PASS画像IDを特定し、その**1点だけ**を制作・検査・保存する。完了と確定するまで別IDには進まない。
- **やり直し**：対象の直前の未PASS画像を規定上限内で再試行。バージョン改訂時は変更点を記録し、不採用履歴を残す。
- **状況**：state・progress・保存画像の実在を参照して報告するだけ。画像生成・Git変更なし。
- **停止**：それ以上進めず、現在の状態を保持。
- **ID指定**：stateと整合を取ってから着手。既存合格素材は無断上書きしない。
**「次」＝前の画像を無条件にPASSする、ではない。**

## 1枚の制作手順
1. 対象ブランチから`EXECUTION_STATE.json`と`P3_asset_progress.json`、`asset_manifest.json`を再読。次ID、版、固定プロンプトblob SHAを照合。
2. 当該IDの`next_prompt_file`**1件だけ**を全文読込み。画像生成用の意味指示はその原文を使用し、他素材やステータス文を生成器に混ぜない。
3. `materials/slide_references/Sxx.jpg`を画像として確認し、どの空枠の図かを理解する。利用可能なら`materials/style_references/`や`assets/accepted/`の**同じスライドの既存合格画像**も画像として確認。GitHubバイナリを視覚的に取り出せなければ、見たと装わずユーザーにそのファイルの添付を依頼して停止する。
4. ChatGPT内の画像生成機能で独立した素材**1点のみ**を描く。元スライド全体や画像枠のスクリーンショットを最終素材として生成しない。PPTXはこの段階では編集しない。
5. 講義固有の意味契約、必要関係・矢印方向、禁止事項、文字の正確さ、2Dフラット画風、画像の枠に対する視覚バランスを確認。PNG本体にアクセスできる場合はPNG形式・RGBA・本物の透過画素・縦横比・余白を機械検証し、判定をQCログへ記録する。
6. PNG本体を**対象講義ブランチ**の`assets/accepted/{asset_id}.png`（FAILなら`assets/rejected/{asset_id}_vN_attemptK.png`）へ保存。Git blobとSHA256を読み戻せた場合のみGitHub保存完了と呼ぶ。コネクタがGitHubのバイナリ書込みに対応しないなら、PNGをチャットからダウンロード可能にし「GitHub保存未完了」と明記して停止し、ユーザーのコミットを待つ。
7. 対象ブランチの`qc/`、`P3_asset_progress.json`を更新し、**最後に**`EXECUTION_STATE.json`をSHA競合検出付きで更新。次IDへ移行するのはPASS画像が実際にGitHubで取得可能なときだけ。

## 必須描画規則
- 独立した透明背景の教育用2Dフラット図。スライド全体、本文、Takeaway、表、画像ID、実際には存在しない図や役割を描かない。
- ベースの色・線幅は`major/design_system_general_final.md`と`major/content_visual_policy_final.md`、講義ブランチの元スライドに合わせる。
- 教育的な理解に必要な工程名・役割名・各パーツのラベルと補助説明句は積極的に許可し、ラベル数・語数に一律の上限を設けない。誤字、判読不能文字、内容無関係の文章、意図しないロゴ、スライド本文の丸ごと複製は不可。
- 矢印・循環・比較対象の誤解を招く表現はFAIL。各素材の意味契約が共通ルールより優先。
- 生成物だけでなく元スライドの指定枠に等比仮配置したプレビューで密度・文字の衝突・余白を評価できると望ましい。
- 参照JPGやPPTXは*入力資料*、成果PNGは*新規独立素材*。参照からの勝手な全画面変換を禁止。

## 状態管理・停止
- 全15件等の件数と次のIDは**講義側の最新stateだけ**で決める。初期状態の数字を永続的な正本として扱わない。
- 進捗更新は画像実体の保存確認後。保存不能・参照画像を実際に見られない・必要情報に矛盾・不合格はPASSにしない。
- 同一素材/固定プロンプト版は原則初回を含め最大3回。3回FAILならBLOCKED。新版を作るときは旧失敗を残す。
- 外部API/GitHub Actionsは使用しない。GitHub Secretは使わず、GitHub privateのまま。
- ブランチの混在を防止。**majorはルールだけ、講義ブランチは素材だけ**。旧`minor`や`main`を現在の進捗の正本としない。
- 複数チャットから同時に同じstateを更新しない。ハッシュが不一致なら再取得・確認してから更新する。

## 画像生成ツール・コネクタの限界
ChatGPTがGitHubの画像バイナリをそのまま視覚参照できるか、生成後の画像をGitHubへ直接コミットできるかは利用できるツール次第である。未検証のまま「GitHubだけで完全自動」と報告しない。実バイナリにアクセスできない場合は該当ファイルの一度の添付、コミットができない場合は手動アップロードを依頼する。
