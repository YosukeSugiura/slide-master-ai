# ChatGPT 4段階制作コントローラ v2.0

> 入口 `CHATGPT_NEXT.md`。本書は新規・再制作デッキの**標準**。旧 `CHATGPT_STEP_CONTROLLER_v1.md` は3枚試作の履歴であり本書が優先する。

## 1. ワークフローと責任境界

正本 `docs/workflows/LECTURE_SLIDE_PRODUCTION_4PHASE_v1.md`。
`P1_SPEC`（初回の制作プロンプト、内容指示書）→`P2_PPTX_SKELETON`（「次」①、全ページ骨組み＋全素材生成指示書）→`P3_IMAGE_ASSETS`（「次」②、**独立画像だけ**）→`P4_FINAL_PPTX`（「次」③、画像挿入・全ページ実レンダリング・完成）。

**PPTXスキルと画像生成は同じ段階内で混在させない**。P1: 内容設計、P2: PPTX制作（画像生成しない）、P3: 画像生成（PPTX編集しない）、P4: PPTX制作（画像生成しない）。画像の意味違反はP3へ差し戻す。生成プロンプト案と実効入力は区別して記録。

## 2. 状態と操作

新規runのSTATEはデッキ固有の `docs/runs/<run_id>/STATE.md`。このプロジェクトの例: `docs/runs/lecture03_48slides/STATE.md`。**旧3枚のSTATEは参照のみ**。毎コマンド直前にGitHub minorから再取得する。

| 状態 | 意味 |
|---|---|
| `AWAITING_BRIEF` | 対象デッキが選定され、P1のユーザープロンプト待ち。「次」だけではP1開始しない |
| `READY` | 指定ステージへの「次」で開始可 |
| `RUNNING` | 実行中・中断後は既存成果物を検証して再開 |
| `BLOCKED` | 必須入力/成果物/品質が未達。原因を報告し修正後に同じステージから再開 |
| `WAIT_CONFIRMATION` | 課金・権限・原稿の重大変更等、個別の明示承認が必要 |
| `PAUSED` | ユーザー指定の停止 |
| `DONE` | P4の全合格ゲート完了 |

- `初回の講義制作プロンプト`: P1の元原稿・要件を指定し、P1を実行。素材が既にGitHubにある場合はその対象を一意に指定すればよい。仕様が不完全なら確認し、P1未完成で先へ進まない。
- `次` / 通常進行への`はい`: **現在ステージの全未完了項目を**可能な限り連続処理。完了検証・成果物保存・ログ・STATE更新後に後続ステージに進める。後続の実作業はユーザーの次の「次」まで開始しない。
- `次`でリソース/時間上限に達した場合：同じステージの`IN_PROGRESS`を記録し、**次の「次」は同じステージを再開**。ユーザー承認操作の回数は標準では初回＋「次」3回を目指すが、処理上限によって増える場合がある。
- `状況`/`確認`: STATE・ログ・実在するプレビューを報告（実行・ステージ進行なし）。
- `やり直し`: 未合格項目のみ版を追加し最大試行枠で実行。合格済みの無断上書き禁止。
- `止めて`: PAUSEDへ移行。 `再開`: PAUSED→READYにするのみ。 `差戻し`: 要修正ステージとその下流影響を記録し、既存合格判定を必要範囲だけ無効化。
- `AWAITING_BRIEF` または `BLOCKED` から、意味が不明な「次」で自動的に成功にしない。

## 3. ステージ進行のトランザクション

1. STATE・元原稿・仕様のSHA/版を読み、依存物・使用可能ツールを確認。RUNNINGへ先行更新する場合は競合検出し、実行単位とログIDを記録。
2. 作業を**ページ/画像単位で内部管理**。各アイテムの `TODO/IN_PROGRESS/PASS/FAIL/BLOCKED` を記録。1回の「次」で特定の画像1点しか処理しない旧仕様は適用しない。
3. 単体ゲート＋ステージ全体ゲートで判定する。**PASSのときだけ**成果物のSHA・保管先・実在と後続からの取得性を検査する。曖昧な合格・未評価の水増し禁止。
4. まずログ・manifestを保存、**最後にSTATEをblob SHAで更新**する。衝突したら再取得して調停。バイナリをGitHubにアップロードしたと主張するには実際の保存と再取得確認が必要。
5. 失敗/保存不能/課金許可待ちは`BLOCKED`または`WAIT_CONFIRMATION`で同じステージを保持。作業量上限の中断は`READY`と未完了内訳を残して再開。後続ステージを実行しない。
6. DONEはP4全ページPASS、全素材PASS、入出力照合・品質監査・納品の実行確認のときだけ。

## 4. 画像境界と検証

画像生成は`docs/IMAGE_GENERATION_STAGED_WORKFLOW_v2.md`だけをSTEP3で適用。**生成対象はその素材IDの独立画像1点**。イラストの対象と行動・工程・接続を肯定形で指示し、タイトル/Takeaway/本文/スライド全体/他素材を生成しない。分類Cは画像ゼロ。
元テキスト・表はPPTXで編集可能。A主図の誤った接続はPPTX矢印等で後付け修復しない。画像生成ツールの実効プロンプトが不可視なら未確認と記録。初回+最大2再試行/素材。合格がなければBLOCKED。

## 5. PPTXとデザイン

実際のPPTXを全ページレンダリングし、文字切れ/重なり/余白/画像比率/表の厳密一致/原文逐語/可読性/編集可能性を検査。`design_system_general_final.md` v2.2、`content_visual_policy_final.md` v2.8、承認済みの大きな主図・ゆとりのある余白、18ptまとめ文が独自情報を持つ場合のみ薄いグレー背景とするルールを維持。
源真ゴシックPの名前をPPTXに指定しただけで実書体を導入・描画したと報告しない。実書体がなければ代替レンダリングと合格条件の制約を明示する。

## 5.1 STEP2バッチチェックポイント（48枚版の特則）

`P2_PPTX_SKELETON` を1回で全48枚作成して最後まで一切保存しない実行は禁止。`docs/workflows/STEP2_BATCH_CHECKPOINT_v1.md` に従い、**6枚ずつ組立・検査、2枚ごとにGitHubへ進捗/QC/制作コードをcommit**、生成PPTX/PDF/PNGを検証済み永続保存先へアップロードする。工程途中の48枚草稿は未検証として扱い、進捗を示す証拠と混同しない。大工程はあくまでP2のままで、次の「次」は残り未検証ページの続きから進む。

## 6. ストレージ・権限・中断

- 指示書、素材manifest、実行結果、STATEをGitHubのprivate minorへ記録。画像・PPTX・PDFは実際に再取得できる保存先を検証し、保存不能なら先へ無条件に進まない。チャット一時sandboxは永続保存と呼ばない。
- 無承認の追加有料Image API、Codex外部委任、第三者へのアップロード、GitHubの公開化、元原稿の破壊的改訂を行わない。
- 一時的な実行制限を超えて1応答で48枚・全画像が完成するとは保証しない。**品質ゲートを省略して操作回数を減らすことは禁止**。
