# ChatGPT 対話型ステップ実行コントローラ v1.0

## 1. 目的・位置付け

長文の依頼を毎回書き直すのではなく、ユーザーが「次」「はい」「状況」「やり直し」と一言だけ入力して、ChatGPTの通常チャットでスライドの画像生成・PPTX組立・実レンダリング・合否判定を順に完遂できるようにする。タスクの全工程・判断条件・ログはGitHubへ保存し、ChatGPTに依頼する文章は短くする。

これは既存の運用モードとは**別の「対話型ステップ実行モード」**である。第10.4節の手動レビュー型「毎画像の承認待ち」、第10.6節の自動一気通貫型「一度の依頼で全部実行」をいずれも強制しない。ユーザーが「次」と入力した場合、この対話型モードが優先する。**1工程は複数ツール呼出しを含んでもよいが、工程の途中で不必要にユーザーへ作業を返さない。**

## 2. 正本と入力資料

正本：
- 入口：CHATGPT_NEXT.md
- 手順：docs/workflows/LECTURE03_ABC_AND_3SLIDES_v1.md
- 最新進捗：docs/runs/lecture03_three_slides/STATE.md
- 記録：docs/runs/lecture03_three_slides/logs/ 以下（成功・失敗とも追記し、履歴を消さない）

内容・デザインの正本：
- design_system_general_final.md
- content_visual_policy_final.md
- docs/lecture03_48_selected_3_contents.md
- docs/IMAGE_GENERATION_STAGED_WORKFLOW_v1.md

各コマンドの開始時に、GitHub minor の STATE.md を**必ず新規取得**する。このチャットの説明・記憶がSTATEより古い可能性があるため、進捗を会話から推測しない。最新の仕様を確認し、STATE上の current_step のみ実施する。

## 3. 状態とコマンド

STATEの主なキー：status、phase、current_step、last_completed、attempt、blocking_reason、last_log、output_manifest、spec_refs。

状態の意味：
- READY：ユーザーの「次」「はい」により current_step を実行可能。
- RUNNING：現在の工程を実行中。前回の応答が中断した場合、生成物・前回コミットを検証して重複実行を避ける。
- BLOCKED：工程の合格条件を満たしていない。無断で次工程に進まない。「やり直し」で再試行可能な場合をログに記す。
- WAIT_CONFIRMATION：追加料金・権限・危険な破壊的変更など、必要な具体的確認を提示済み。単なる「はい」だけで包括的な有料契約等へ拡張しない。
- PAUSED：ユーザーが停止を要求。
- DONE：最後の工程まで合格。

「次」または通常進行への「はい」：
1. STATEを読み、current_step、入力・依存物・使用可能なツールを照合。
2. 必要に応じて STATEをRUNNINGへ先行更新（GitHubの更新が可能な場合）。再実行に備えて試行番号を増やす。
3. その工程の作業を最後まで実行。図の工程なら生成後の意味評価まで、PPTX工程なら実ファイルの制作・レンダリング・検査まで**同一ユーザー応答内で行う**。
4. 結果が合格なら、実行ログ・成果物の実在を確認して STATE.current_step を後続工程へ進め、statusをREADYにする。未達なら BLOCKEDを記録してcurrent_stepを維持。結果不明は成功にしない。
5. 最終返答は「完了した工程／検証結果／成果物／次の工程」の短い日本語のテキスト。文字を含む生成画像で手順を説明しない。
6. **ユーザーから次の入力が来るまでは後続工程を実行しない。** バックグラウンドで処理が継続すると主張しない。

「状況」「確認」：STATEとログを読むだけ。未実施の画像生成・PPTX実行は行わない。
「やり直し」：同一 current_step の新たな試行を記録して再実行。既存素材を上書きせず _v2、_v3 など別版にする。初回を含め最大3回の通常試行を基本とし、反復する範囲違反は別方式検討として BLOCKEDにする。
「止めて」：実行停止・必要に応じてPAUSEDをコミット。
「再開」：PAUSEDからREADYへ復帰するだけ。次工程の実行は次の「次」から。

## 4. 画像生成の責務分離

ChatGPTの画像生成器へは**「今回必要な独立したPNGイラスト1点」**だけを対象として渡す。画像生成器がPPTXやA/B/C実験表全体を描くように依頼してはいけない。講義内容は手順管理・プロンプト設計の根拠として使用するが、画像入力文脈にスライドタイトル、PPTX作成指示、比較実験の採点表、他の素材等を混入しない。ツール内部の実効プロンプトが観測できない場合は「実効プロンプト未確認」と記録する。

各素材の実行時に第10.2節の6フィールド、10.3節の10ゲートを満たすこと。正確な本文・ラベル・表はPPTX側の編集可能オブジェクトにする。生成した画像がスライド全体や疑似文字入りの場合は不合格で採用しない。合格画像だけを統合する。最大3回で合格しなければ BLOCKEDとし、評価軸・失敗画像を残す。

## 5. PPTXとファイルの検証

PPTXが指定された工程では、必要ならプログラムで編集可能な図形・テキスト・表を作り、生成画像をその挿入範囲に配置する。必ずその**実際のPPTXファイル**をレンダリングし、画像プレビューから文字切れ・重なり・余白・関係・可読性を評価する。指定フォント源真ゴシックPのPPTX名設定と、レンダリング環境での代替フォントを区別する。元原稿の用語・日本語句読点を改変しない。比較方式名のA/B/Cと図分類A/B/Cを混同しない。

## 6. GitHub保存のトランザクション

- 各工程を始める前に最新のSTATEを取得し、更新は現在のblob SHAとブランチを指定する。他の更新と衝突したらSTATEを再取得して整合を確認する。
- 合格結果の記録では**まず成果物の実在を検証、次にログを保存、最後にSTATEを更新**する。未完了時も、失敗理由と現状が分かるようにログ・STATEを保存する。
- 各工程のログには timestamp（確認できる場合）、step_id、試行番号、使用仕様の版、入力、観測できたツール入力、出力ファイル名・実在性、合否、原因、次操作を記録。
- 通常のテキスト指示書・ログ・状態はGitHubにコミット。PNG、PPTX、PDFなどの成果物は接続機能と容量が対応するときのみ実アップロード。未アップロードならGitHubへ「unpublished artifact」の状態を正直に残し、当該チャットでリンクを提示する。チャット固有のsandboxパスが新チャットでも有効と推定しない。新チャットへ引き継げないバイナリがあれば元ファイルの再添付か保存先の明示が必要。
- GitHubは非公開を維持する。外部有料API課金、既存内容原稿変更、公開権限変更、他アプリへの自動送信を独断で行わない。

## 7. 品質判定と進行

工程の PASS の定義はrunbookに従う。「ファイルを作った」だけでは合格にならない。画像の場合は独立性・学習内容との意味一致・疑似文字・背景・画風の検査、PPTXの場合は原文一致・編集可能性・実レンダリングを検査。明確なNG・未確認の条件があるなら BLOCKED。

比較実験は *同一条件での実験結果* と *以前の流用画像による参考試作* を厳密に区別し、未実施方式に点数をつけない。実験結果だけで全スライドの方法を確定できない場合、選定理由と不確実性を記録する。

## 8. 読み込み失敗時の挙動

同じチャットでも新しいチャットでも、正本が取得できなければ「次」を推測で実行しない。閲覧できないGitHubファイル名・ブランチ・取得エラーを報告する。ファイルを以前に読んだ事実は最新STATEの代わりにならない。
