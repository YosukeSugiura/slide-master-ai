# STEP 2 安全実行・小分け保存手順 v1.0

> 2026-10-14導入。48枚版STEP2（`P2_PPTX_SKELETON`）の**内部実行方式**。4段階の大工程は変えない。直前の長時間一括実行が中断したため、「先に48枚を一度に作って最後に検査・保存する」方法を禁止する。

## 1. スライド単位の安全な分割と操作数

- **6枚×8バッチ**：B01=01–06、B02=07–12、B03=13–18、B04=19–24、B05=25–30、B06=31–36、B07=37–42、B08=43–48。
- ユーザーの「次」はSTEP2の**未完了バッチを可能なだけ連続実行**する指示。バッチごとの承認は不要。実行制限で停止した場合だけ、次の「次」で同じSTEP2の続きから再開。
- 各バッチ内では**1枚ずつ構築→構造チェック→ローカルの一時PPTXとチェックJSON保存**。**2枚ごとにGitHubへ進捗・検査情報を小刻みにcommit**。可能であれば同時にPPTXを永続保存。**6枚終了ごとにバッチPPTXを実レンダリングし検査**してからバッチ完了を記録。
- 「6枚」とは1回で処理しなければいけないノルマではない。品質未達、ツール制限、停止時は**合格済みページを維持**して中断する。

## 2. 信頼できる保存先と回復方針

- **GitHub minor**：`docs/runs/lecture03_48slides/step2/checkpoints.json`（ページごとの最新status、完了時刻、SHA256、バッチ、依存元ハッシュ）、`step2/logs/BXX*.md`（結果・欠落・原稿照合・QC）、`step2/image_prompts/...`（完成した独立画像生成指示書）、必要なら再生成可能なビルドスクリプトを保存。
- **成果物PPTX等のバイナリ**：GitHubへ直接commitできた時のみそのGitHubパスを永続保存場所として採用。認証済みGitHub APIのテキスト専用create_file/update_fileでは**PPTXの実バイナリを保存したことにはならない**。
- GitHubバイナリが難しい場合はユーザーの**ChatGPTファイルライブラリ** `/SlideProjects/lecture03_48slides/step2/` へPPTX/PDF/プレビュー等をアップロードし、実行後にファイルの存在を再検証。GitHubにはライブラリの実パス・ファイルID・SHA256を含む回復記録を保存。原稿・JSON・画像生成指示書はGitHubに保存。バイナリの所在が不明ならPASS禁止。
- **暫定48ページ草稿は** `48pages_UNVALIDATED_recovery_draft.pptx` に退避済みだが、文字サイズ・原文保持・全ページの実レンダリングを合格していないため **UNVALIDATED / NOT PASS**。再利用可能な構造（ページ順、画像15枠のID）は参考にできるが品質ゲートは免除しない。
- ステージ切替前には全8バッチと全48枚の実存在、原文対応、欠落なし、15画像枠の座標とプロンプトの完成、全ページの最終一括レンダリングを確認する。**全バッチのPASSがそろうまで`P3_IMAGE_ASSETS`へ進まない**。

## 3. バッチのPASS条件

1. 入力は `docs/lecture03_48_slide_contents.md` と `docs/runs/lecture03_48slides/slide_plan.json`。原稿ファイルのSHAが変わったら該当ページを再検査。
2. タイトル・Intro・Takeaway・厳密な表/数値/UI/実習プロンプトが原文一致。説明文短文化は意味対応が確認済み、内容削除禁止。
3. 4:3、共通デザイン定義v2.2、視覚方針v2.8、承認済みの11/17/35再設計スタイル。不要なカードなし、主図を大きく、18pt補足は重複がないときだけ薄灰 `#F3F4F6`。
4. 分類Cの正確な図・表・UIは編集可能。A/Bは**独立画像をまだ生成しない**。既存合格イラストを勝手に転用しない。
5. バッチのPPTXから直接PDF/PNGを生成し、全ページ目視で文字切れ・重複・狭さ・重要な矢印関係を点検。不合格はPASSさせない。未導入の源真ゴシックPについては代替書体での検査と明記。
6. 画像対象ページは `asset_id`→枠 `x,y,width,height,aspect_ratio` (inch)が1対1。枠の設計が本当に確定した後にだけSTEP3用の**独立画像1点だけ**を作る完全プロンプトと事前10ゲートを保存。
7. 保存したPPTX、各プレビュー、ビルド源・manifestのハッシュを計算し保存先に実在することを確認。後続の別チャットから再取得可能か検証。**書面ログだけでバイナリ保存済みとしない**。

## 4. 中断とSTATEの扱い

- `STATE.md`の`current_step`は`P2_PPTX_SKELETON`のまま。内部進捗は`step2/checkpoints.json`で管理（`B01`など）。
- ページステータス：`TODO`、`IN_PROGRESS`、`DRAFT_UNVALIDATED`、`PASS`、`FAIL`、`BLOCKED`。バッチは全ページPASS・全成果物保存検証済みの場合のみPASS。
- **前の応答がハングしたとき**：まずGitHub progress、ライブラリ保存済PPTX、ローカル成果物を読み戻す。最後の成功したチェックポイントから再開。壊れた/欠落ファイルはPASSにせず該当ページだけ再作成。
- GitHubには必ず「何ページまで完了、何が未検証、再開位置、利用可能な実ファイル」が残るようにする。
- 1回の処理時間が長いときは途中でユーザーへ実作業の進捗を短く報告。出力を溜め込んでから最後に一括保存しない。
